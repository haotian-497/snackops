# SnackOps 需求优先级

> SnackOps 是一个零食电商客服 Agent 运营台，核心命题是验证「规划 + 查数 + 话术 + 风控审核」这条客服编排链路能否成立，并让它可运营、可持续改进。

## 分层逻辑

| 档位 | 目标 | 包含模块 |
| --- | --- | --- |
| **P0** | 验证架构命题 | Demo 零依赖演示 · Agent 编排管线（Planner→Tool→Skill→风控）· 业务查数与种子数据 · 运行留痕 |
| **P1** | 做到可上线运营 | 真模型多厂商接入 · Skill/Planner 可编辑与版本快照 · 运行监控 · 测评跑批与标注 |
| **P2** | 构建数据改进飞轮 | 坏回复改进闭环 · Prompt A/B 实验 · 版本回滚中心 · LLM-as-Judge |

## 三条核心取舍

1. **先证明编排对，再换发动机。** P0 用本地确定性 Demo 跑通整条链路，而不是急着接真模型——架构错了换什么模型都白搭；架构对了，接 DeepSeek 还是 GPT 只是换个 Base URL。
2. **安全和性能是第一天的事，不是二期优化。** 风险审核（拦截 + 改写）和「运行列表不塞全量 trace、记录封顶 200 条」放在 P0，因为它们决定的是"敢不敢给人看"，而不是"好不好用"。
3. **运营飞轮是数据依赖的，顺序不能倒。** 监控、测评、标注是 P1 的基建；改进、A/B、回滚是 P2 的飞轮——没有前者攒下的运行数据和版本，后者就是空界面。

<summary>▶ P0 明细：核心闭环 MVP（展开看）</summary>

**判断标准：砍掉它，这个产品是否还成立？** 成立就不放 P0。

| 需求模块 | 具体内容 | 为什么必须 P0 |
| --- | --- | --- |
| Demo 演示模式 | 本地确定性回复，不调外部模型、无需任何 API Key | 面试/作品集现场零依赖是硬约束；没有它，演示先死在"你 Key 呢" |
| Agent 运行管线 | Planner 规划 → Validator 校验 → Tool 查数 → Skill 生成 → risk-check →（拦截则 rewrite）→ 回复，SSE 流式 | 产品本体。这是"客服 Agent"和"套壳 ChatGPT"的本质区别 |
| 六个查数 Tool | 商品 / 活动 / 优惠券 / 订单 / 物流 / 价格试算 | 客服必须基于事实回答，没有这层就是在编 |
| 最小 Skill 集 | 需求抽取、回复生成、risk-check、推荐决策、转人工判断 | 覆盖售前推荐 + 售后分类 + 安全审核三条主路径，再多是过度设计 |
| 工作台 | 一个输入框 + 执行时间线 + 最终回复 | 唯一需要给人看的界面，其他后台一律不做 |
| Run 落盘与存档 | 记录写 JSON，列表只传摘要（不带 steps/plan 全量），最多保留 200 条 | 可追溯是底线；"列表不塞全量 trace"是主动工程取舍——早期版本因此卡死过页面 |
| 业务种子数据 | 商品、订单、券、物流、退换政策、FAQ、转人工规则 | Demo 的事实底座 |
| LLM 不静默降级 | 真模型缺 Key / 报错时返回结构化中文错误，绝不悄悄切回 Demo | 安全底线。演示时"假成功"比报错致命 |

**P0 主动砍掉**：真实模型接入、编辑后台、监控大盘、测评、标注、A/B、回滚——它们服务于"运营"，但 P0 先回答"Agent 答得对不对"。

<details>
<summary>▶ P1 明细：可运营化（展开看）</summary>

**判断标准：没有它，P0 演示能成立，但真接一个商户就不敢上线。**

| 需求模块 | 具体内容 | 为什么是 P1 |
| --- | --- | --- |
| 真模型接入 | OpenAI 兼容协议；DeepSeek / OpenAI / 通义 / Kimi / 智谱预设；按厂商分槽位存 Key，切厂商互不覆盖 | Demo 只够证明架构；真上线必须换发动机。槽位设计为多人演示/多商户复用 |
| 密钥与错误处理 | Key 只存本地 gitignore 文件、界面脱敏；区分鉴权失败/模型名错/超时/请求失败四类中文错误 | 真接外部服务后，"报什么错"本身就是产品质量 |
| Skill / Tool / Planner 可编辑 + 版本快照 | 页面改提示词与描述，改前自动打快照，可 diff | 运营要能改话术而不是改代码；快照是后续一切回滚的前提 |
| 运行监控 | 今日/7天 KPI、成功率、耗时、状态分布、风险审核分布、失败步骤 Top | 没有观测就是盲飞 |
| 测评集 + 跑批 + 规则评分 | 维护 case 集，批量跑 Agent，按关键词/禁词/期望 skill 打分 | 改提示词后必须有回归手段，否则"可编辑"反而是风险 |
| 服务评价 + 数据标注 | 用户/运营打分，对坏回复多维标注 | 收集坏回复样本，喂给后续改进 |
| Demo 一键重置 | 一条命令恢复演示种子，保留业务数据与已存 Key | 演示效率工具，不影响产品成立，排最后 |

</details>

<details>
<summary>▶ P2 明细：持续改进飞轮（展开看）</summary>

**判断标准：它依赖 P0/P1 已积累的运行数据和基建，过早做就是空转。**

| 需求模块 | 具体内容 | 为什么只能 P2 |
| --- | --- | --- |
| 改进建议闭环 | 从低分/标注→根因诊断→生成新 prompt→晋升为测评 case | 需要 P1 的标注数据和测评基建喂着，没样本时无米下炊 |
| Prompt A/B 实验 | 克隆 Skill/Planner 候选 → 双批次测评 → 对比 → promote / discard | 没有 P1 的"跑批+评分"就没有对比基准 |
| 版本回滚中心 | 聚合 Skill/Planner/Tool/Judge/LLM 所有版本快照，一键回滚、紧急启停 | 建立在 P1 的版本快照之上；没攒下版本就没东西可回滚 |
| LLM-as-Judge | 用模型对回复做 PASS/FAIL/REVIEW 裁决，补充规则评分 | 规则评分覆盖不住开放话术，是规则跑顺后的增强项 |
| 批次对比与 case 详情 | 两个测评批次横向对比，定位退步用例 | 有了多次跑批数据后才有对比意义 |
| 差评→改进→转人工联动 | 低分自动生成改进工单，复杂问题走人工 | 长尾场景，P0 用固定兜底话术即可，不必第一天建工单流 |

</details>
